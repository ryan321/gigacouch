# Giga Couch V1: web games in Chrome

Decided: October 8, 2026.

Giga Couch v1 is a website. People make an account, upload web games, browse what others made, and play in Chrome with the controllers Chrome supports. There is no app to install and no marketplace.

The goal is speed to market. Everything that needs an installed app waits until people are using the site.

## What changed

Everything built before this decision is research and prototyping. It stays in the repo and is not part of v1:

* The Game Browser app: the Electron shell, the Rust loopback host, and the Mac build.
* Phones as controllers, phone views, named actions, the Phone Lab, and the Controller Gallery.
* The Godot SDK, Creator Hub, the native Godot player, and the local library.
* Native controller work: Wii, Switch, and wired USB pads.

Several things carry over:

| From the prototypes | Use in v1 |
| --- | --- |
| The web package format and its checks | Ideas for checking uploads |
| The brand guide and fonts | The site's look |
| Controller research | What to promise players about pads |

## What v1 includes

### Accounts

* Sign up, sign in, sign out, and recover a lost account.
* Each account has a unique handle and a display name.
* Players must be 13 or older. Accounts for younger children wait until there is a parent-consent flow.

### Profiles

* A public page per person: avatar, display name, handle, a short bio, and the games they published.
* People edit their own profile.

### Upload games

* A creator uploads a zip of a web build with `index.html` at its root. Builds exported from Godot, Unity, three.js, Babylon.js, PlayCanvas, or plain JavaScript all qualify.
* The creator fills in a title, a description, a cover image, up to six screenshots, tags, and what the game supports: keyboard, mouse, or gamepads, and from one to four players.
* A game starts as a draft that only its creator can play. Publishing makes it public. An unlisted game is playable by anyone with its link but doesn't appear in browsing or search.
* Uploading a new build replaces the live one. The previous build is kept so the creator can roll back.
* The creator can unpublish or delete a game.

### Browse

* A home page with new games and popular games. Featured games are picked by us.
* Search by title, creator, and tag.
* Filters for player count and for controller, keyboard, or mouse play.
* A page for each game, with its cover, screenshots, description, creator, supported controls, and a Play button.

### Play

* Play opens the game full screen in a sandboxed frame. Clicking Play also lets Chrome start sound and full screen, which both need a click.
* Before the game starts, a short controller check shows which pads Chrome sees, and asks players to press a button on each one.
* The page counts plays, which feeds "popular".

### Safety

Any site that hosts uploads needs these before launch:

* A Report button on every game and profile.
* Admin tools to unpublish a game, hide a profile, and suspend an account.
* Terms of service, content rules, a privacy policy, and a copyright takedown process.

## Controllers

V1 supports what Chrome supports, and nothing on top:

* **Gamepads** through Chrome's standard gamepad support. Xbox, PlayStation 4 and 5, Switch Pro, and most pads in XInput mode report the standard layout. Chrome shows a page at most four pads.
* **Keyboard and mouse**, including mouse lock for first-person games.
* **Rumble** where Chrome supports it for that pad and operating system.

The game page states which of these the game uses. Pads appear to a game only after someone presses a button. The controller check gets that press out of the way.

Games read pads directly through Chrome's gamepad API. A small optional helper script for creators, with player join and standard button names, can come later. It isn't needed to launch.

The R&D samples won't run unchanged. The Controller Gallery and Phone Lab use the Game Browser's bridge, which doesn't exist in plain Chrome.

## Browsers

* **Supported:** desktop Chrome on Windows, macOS, ChromeOS, and Linux.
* **Not blocked:** Edge and other Chromium browsers will mostly work, but aren't tested. Safari and Firefox get a note that the site is built for Chrome.
* **Phones and tablets** can browse, sign in, and manage games. Playing is meant for a computer with a TV or monitor.

## How games are hosted

### A separate domain for games

Uploaded games are creators' code, so they never run on gigacouch.com. A game on that domain could read players' sign-in cookies and act as them.

* Games are served from a separate domain, with a name still to be chosen. Each game gets its own subdomain, so games can't read each other's saved data.
* That domain should be on the Public Suffix List, as github.io is. That stops one game from setting cookies for every other game.
* The play page on gigacouch.com embeds the game in a sandboxed frame, and grants it only gamepad, full screen, sound, and mouse-lock access.

### What the game server must do

* Serve `.wasm` files as WebAssembly, and serve Unity's compressed `.br` and `.gz` files with the right encoding headers.
* Send long cache headers for build files. Each build gets a new address, so caching never serves an old build.
* Serve only static files. Games have no server code in v1.

**Threaded builds are out for v1.** Godot's threaded web export and Unity's multithreaded builds need a special page isolation that conflicts with embedding the game in our page. Godot 4.3 and later can export without threads, and Unity's web builds use one thread unless told otherwise. The upload checker should spot a threaded build and say how to re-export it.

### Upload checks

* The zip has `index.html` at its root, no paths that leave the folder, and no links to other files.
* Size limits apply to the whole game and to each file. The exact numbers are still to be decided.
* Only known web file types are allowed.
* A failed check lists every problem in plain words, so the creator can fix them all at once.

## Saves

Games keep their saves in the browser, on their own subdomain. Saves stay with that browser on that computer. Clearing site data or using a private window loses them. Cloud saves tied to accounts come later.

## Building blocks

| Part | Plan |
| --- | --- |
| Site and API | A Next.js and React app in `apps/site`. It's a new app; the Rust platform server in `crates/platform` stays as R&D. |
| Database | SQLite locally, through Node's built-in SQLite. Neon PostgreSQL in production, reached only through the site's server. |
| Files | On disk locally. In production, object storage for uploads, game builds, covers, and screenshots, with a CDN in front of the games domain. |
| Upload processing | Unzip, check, and store under the game and build. It runs in the site's server for now; production should run it apart from the main server. |

## Not in v1

* A marketplace, paid games, or creator payouts.
* Phones as controllers, and motion controls.
* More than four pads.
* A desktop app, offline play, and downloads.
* Native Godot games.
* Per-person saves and cloud saves.
* Online multiplayer.
* Comments, follows, and friends, unless they're chosen for launch below.

## Status

The site runs locally in `apps/site`, with SQLite and files on disk. It has:

* **Pages:** a landing page with a live controller panel, sign up and sign in, profiles, and upload.
* **Browsing:** browse with search and filters, and a page for each game.
* **Owner tools:** edit, new builds, and delete.
* **Play:** a full-screen play page with a controller check.

Games are served from a second local origin, `127.0.0.1`, as a stand-in for the separate games domain. Account recovery, safety tools, rollback, and production hosting are not built. [apps/site/README.md](../apps/site/README.md) explains how to run it.

## Order of work

1. **Decide the open questions** below.
2. **Accounts and profiles,** moving to Neon for production.
3. **Upload, checks, and hosting** on the games domain.
4. **Game pages, browse, and search.**
5. **Play page:** the sandboxed frame, full screen, and the controller check.
6. **Safety:** reporting, admin tools, and the legal pages.
7. **Launch games.** People need something to play on day one, so 15 to 20 good games should be on the site at launch. They should cover single-player, local multiplayer, keyboard, and pads.
8. **Launch checks:** Chrome on Windows and macOS with Xbox, PlayStation, and Switch Pro pads; uploads from Godot, Unity, and three.js; backups and a restore drill.

## Open questions

| Question | Recommendation |
| --- | --- |
| How do people sign in? | Sign in with Google, plus sign-in links by email. Chrome users nearly all have Google accounts, and we store no passwords. |
| What is the games domain? | A short, separate domain, added to the Public Suffix List |
| Where are files stored? | Object storage that works well with Fly, such as Tigris or Cloudflare R2 |
| How big can a game be? | Large enough for a typical Unity web build, with a lower limit for each file |
| Which social features ship at launch? | Plays and likes at launch. Follows and comments later, because comments need moderation. |
| Are games reviewed before they go public? | Publish at once, and act on reports. A creator's first game could wait for a quick review. |
| Are Safari and Firefox blocked? | No. They show a note that the site is built for Chrome. |
